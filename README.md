# ВышКат (VyshKat) — Сервис кикшеринга НИУ ВШЭ

Консольное приложение для автоматизации и учёта парка сервиса «ВышКат» в рамках домашнего задания №1 по курсу «Конструирование программного обеспечения» (ФКН НИУ ВШЭ).

Приложение обеспечивает интерактивный учёт техники и инвентаря, прохождение обязательного технического осмотра перед постановкой на баланс, расчёт совокупного суточного энергопотребления флота, фильтрацию устройств для новичков и формирование полного реестра имущества.

---

## Архитектура и принципы SOLID / GRASP

Проектирование выполнено без избыточного усложнения (KISS/YAGNI) с чётким разделением ответственности по пакетам: доменные интерфейсы и модели (`internal/domain`), прикладная бизнес-логика (`internal/service`), консольный интерфейс ввода/вывода (`internal/ui`) и конфигурация DI-контейнера (`internal/di`).

### Ответы на обязательные вопросы:

1. **Какой принцип применён наиболее явно и где:**
   * **ISP (Interface Segregation Principle):** Интерфейсы в `internal/domain/interfaces.go` разделены на узкоспециализированные контракты:
     * `InventoryItem` — базовый контракт для всего, что ставится на баланс (`GetInventoryNumber()`, `GetName()`).
     * `EnergyConsumer` — контракт только для устройств с суточным расходом электроэнергии (`GetDailyEnergyConsumption()`).
     * `RentalVehicle` — контракт прокатной техники (`GetBeginnerScore()`, `IsSuitableForBeginners()`).
     Благодаря этому механический велосипед (`RegularBike`) и шлем (`Helmet`) реализуют только подходящие им интерфейсы и не обязаны реализовывать методы расчёта расхода батареи.
   * **DIP (Dependency Inversion Principle):** Сервис управления флотом `FleetService` (`internal/service/fleet_service.go`) не зависит от конкретной реализации сервисного центра, а принимает абстракцию `domain.ServiceCenter` через конструктор (*Constructor Injection*). Связывание с реализацией `StandardServiceCenter` выполняется внешним DI-контейнером `dig` в `internal/di/container.go`.
   * **SRP (Single Responsibility Principle):** Сущности предметной области инкапсулируют состояние и валидацию данных; `FleetService` изолированно управляет реестром флота и уникальностью инвентарных номеров; `StandardServiceCenter` содержит правила пригодности к эксплуатации; `CLI` изолирует ввод/вывод в терминале.
   * **LSP (Liskov Substitution Principle):** Все реализации `domain.RentalVehicle` (`ElectricScooter`, `ElectricBike`, `RegularBike`) взаимозаменяемы при вызове `FleetService.AddVehicle` и при техосмотре. Конструкторы сущностей гарантируют соблюдение инвариантов (оценка сложности строго в диапазоне 1–10, неотрицательный суточный расход энергии), исключая появление объектов в некорректном состоянии.

2. **Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо:**
   * Сознательно ограничен принцип **OCP** в консольном интерфейсе `internal/ui/cli.go`: выбор и создание конкретных структур (`ElectricScooter`, `ElectricBike`, `RegularBike`, `Helmet`, `ChargingStation`) реализованы через прямое ветвление `switch`, а не через вынос динамического реестра фабрик / плагинов. Для учебного CLI-приложения введение Abstract Factory или Service Registry на данном этапе было бы необоснованным усложнением (overengineering), противоречащим принципам KISS и YAGNI.

## Расширяемость системы

* **Склад запчастей (`Warehouse` / `SparePart`):** Для склада запчастей создаётся отдельный сервис учёта (например, `WarehouseService`). Сами запчасти (`SparePart`) реализуют интерфейс `domain.InventoryItem` (если подлежат индивидуальному номерному учёту), а сменные аккумуляторы дополнительно могут реализовывать `domain.EnergyConsumer`. Сервис `FleetService` не потребует изменений.
* **Сотрудники службы эксплуатации (`Staff` / `Technician`):** По условию предметной области сотрудники не ставятся на инвентарный баланс, поэтому сущность `Staff` **не реализует** `InventoryItem`. Управление персоналом выносится в независимый контекст (например, `StaffService`), не затрагивая учёт техники.
* **Новый вид транспорта (например, `ElectricMoped`):** Достаточно создать новую структуру, реализующую `domain.RentalVehicle` и `domain.EnergyConsumer`. Вся логика приёмки, фильтрации новичков и расчёта энергопотребления во `FleetService` продолжит работать без изменения единой строчки кода (строгое соблюдение OCP).

## Тестирование и подмена зависимостей

Тесты написаны по шаблону **AAA (Arrange-Act-Assert)** с использованием библиотеки `testify/assert`. Тестовое покрытие бизнес-логики превышает 70%.

### Фиксация поведения и техосмотра:
* **Подмена зависимости:** В `internal/service/fleet_service_test.go` зависимость `domain.ServiceCenter` подменяется тестовым двойником — стабом `stubServiceCenter`, позволяющим детерминированно эмулировать положительное решение техосмотра или отказ.
* **Ключевые тесты:**
  * `TestFleetServiceAcceptsVehicleAfterInspection` — проверяет успешную приёмку транспорта в парк при положительном вердикте техосмотра.
  * `TestFleetServiceRejectsVehicleAfterInspection` — проверяет, что при отказе инспекции техника не добавляется ни в парк, ни в инвентарный реестр.
  * `TestFleetServiceRejectsDuplicateInventoryNumber` — проверяет блокировку коллизий инвентарных номеров.
  * `TestFleetServiceFiltersBeginnerVehiclesByScore` — проверяет граничные условия правила для новичков (балл 5 отсекается, 6 и 9 проходят).
  * `TestFleetServiceSumsOnlyEnergyConsumers` — проверяет подсчёт суточной энергии только по потребителям (`EnergyConsumer`), игнорируя механические велосипеды и шлемы.
  * `TestStandardServiceCenterRejectsBrokenVehicle` — проверяет работу реального сервисного центра и отклонение техники с признаком поломки.

## DI-контейнер и жизненный цикл

В проекте используется контейнер `go.uber.org/dig` (`internal/di/container.go`):
* `FleetService` зарегистрирован как **Singleton** (в рамках графа зависимостей создаётся в единственном экземпляре, сохраняя состояние флота на протяжении сессии).
* `domain.ServiceCenter` внедряется через абстракцию, связываясь с реализацией `StandardServiceCenter`.
* Контейнер используется строго на этапе сборки приложения в точке входа (`cmd/app/main.go`). Использование Service Locator внутри домена или сервисов полностью исключено.
